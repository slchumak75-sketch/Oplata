# Модель данных, расчёты и HTTP API

## Файл данных (JSON, `pkg/model`, `pkg/store`)

Файл по умолчанию: `%AppData%\Oplata\data.json` (переопределение: флаг `-data`, переменная
`OPLATA_DATA`, флаг `-portable` → `oplata-data.json` рядом с exe). Сохранение атомарное
(tmp + rename); перед каждой перезаписью предыдущая версия копируется в `backups/`
рядом с файлом (хранятся последние 20). Файл можно смотреть и править вручную (JSON с отступами),
но структура обязана пройти `model.DB.Validate()` при загрузке.

Инварианты (нарушать нельзя — на них завязаны тесты и GUI):

- **Деньги — только целые копейки `int64`** (`*_cents`) везде: файл, API, расчёты. Никаких float.
- **Даты — строки `гггг-мм-дд`** (`model.Date`). Сравнение строк = сравнение дат.
- `Obligation.amount_cents > 0`. `Payment.amount_cents != 0`; отрицательная выплата = сторно.

```json
{
  "version": 6,
  "settings": {"company_name": "Строймаркет", "currency_label": "руб.", "warn_days": 3,
               "holidays": [{"date": "2025-01-01", "name": "Новый год"}],
               "working_days": ["2025-01-04"]},
  "suppliers":   [{"id": "sup-01…", "name": "АВИДО", "deferral_days": 14, "note": "",
                   "prepayment": false, "on_realization": false, "archived": false}],
  "obligations": [{"id": "obl-…", "supplier_id": "sup-01…", "due_date": "2025-01-15",
                   "amount_cents": 101349, "amount_excl_vat_cents": 84457, "vat_cents": 16892,
                   "delivery_date": "2025-01-01", "doc_number": "ТН-12", "comment": ""}],
  "payments":    [{"id": "pay-…", "supplier_id": "sup-01…", "date": "2025-01-15",
                   "amount_cents": 101349, "doc_number": "ПП-7", "comment": ""}],
  "buyers":      [{"id": "buy-…", "name": "СтройДом ООО", "note": ""}],
  "warnings": ["… предупреждения последнего импорта …"]
}
```

Поля:

- У поставщика и покупателя поля УНП больше нет: `Supplier.unp` удалён в схеме v4,
  `Buyer.unp` — в схеме v5. Старые значения при загрузке игнорируются.
- `Supplier.deferral_days` — сохранённая отсрочка по умолчанию (дней); 0 = срок в день поставки.
  `prepayment` и `on_realization` (схема v5) взаимоисключающи. Если выбран любой режим,
  `Supplier.EffectiveDeferralDays()` возвращает 0, GUI делает поле отсрочки неактивным,
  а сервер игнорирует даже явно переданную отсрочку. Когда API сам считает срок из поставки,
  используется `calc.PaymentDueDate(delivery, effectiveDeferral, settings)`:
  `delivery_date + эффективная отсрочка`, затем ближайший рабочий день ручного календаря;
  в файле всегда хранится явный итоговый `due_date`.
- `settings.holidays` (схема v5) — вручную отмеченные выходные дни на вкладке «Данные»:
  `{date, name}`. `settings.working_days` (схема v6) — вручную отмеченные рабочие даты.
  По умолчанию суббота и воскресенье выходные, будни рабочие; далее применяются эти
  исключения, причём одна дата не может находиться в обоих списках. Даты из
  законодательства приложение само не добавляет.
- `Buyer` — покупатель из справочника «Карточка покупателя»: только `name` и `note`.
  С расчётами не связан, в Excel не выгружается, хранится только в JSON
  (и попадает в резервные копии). Импорт Excel справочник покупателей не трогает.
- `Obligation.due_date` — **срок оплаты с учётом эффективной отсрочки** (дата колонки Excel). `delivery_date` необязательна
  в общем API и отсутствует у импорта из Excel; ручной ввод прихода из ячейки «Поставщиков»
  заполняет её обратным расчётом от `due_date` по эффективной отсрочке и ручному календарю
  (`calc.DeliveryDateForDueDate`).
- `Obligation.amount_excl_vat_cents` и `vat_cents` (схема v3, необязательны) — сумма поставки
  без НДС и сумма НДС. Если разбивка есть, обе суммы неотрицательны и
  `amount_excl_vat_cents + vat_cents = amount_cents` (сумма с НДС); оба нуля означают,
  что разбивки нет (например, импорт из Excel). Всплывающая форма поставки на вкладке
  «Поставщики» вводит одну сумму с НДС и разбивку не заполняет; старые записи с разбивкой
  по-прежнему поддерживаются API, журналом и экспортом.
- `Obligation` = «Приход» в GUI / колонка «Собств» в главном листе Excel; `Payment` = «Оплата» / колонка «Выплаты» (в Excel выплаты с минусом — инверсия только в `excelio`).
- `settings.warn_days` — порог статуса «скоро срок». `seeded_from` — устаревшая пометка бывшего seed в базах, созданных версиями до удаления стартовых данных; в новых базах пусто/отсутствует и сохраняется только для чтения старых файлов.
- `warnings` — показываются баннером в GUI, пока пользователь не скроет (`PUT /api/settings {clear_warnings:true}`).
- `version` (= `model.SchemaVersion`, сейчас **6**). v1→v2: добавлены `Supplier.unp` и
  `buyers`; v2→v3: добавлена разбивка начислений по НДС; v3→v4: `Supplier.unp` удалён;
  v4→v5: удалён `Buyer.unp`, добавлены `Supplier.prepayment/on_realization` и
  `settings.holidays`; v5→v6: добавлен `settings.working_days`. Старые УНП
  игнорируются при загрузке и не записываются обратно. Миграции v1–v5 — в
  `store.Decode`; он также нормализует `holidays`/`working_days` в `[]`, триммит
  названия выходных и сортирует оба списка по дате.
  Менять формат → увеличить версию, добавить миграцию в `store.Decode`/рядом, запись в CHANGELOG и здесь.

IDs: `sup-/obl-/pay-/buy-` + 12 hex-символов (`crypto/rand`); в старых базах, созданных
из бывшего seed, могут встречаться детерминированные `sup-001…`, `obl-000001…`.
Порядок срезов в файле = порядок отображения списков.

**Первый запуск:** встроенного seed больше нет. `store.Open(path)` при отсутствии файла
создаёт и сохраняет пустую базу `model.NewEmptyDB()` (тест `store.TestOpenCreatesEmptyDB`).
Существующий файл данных открывается без очистки. Чтобы загрузить исходный Excel 2025,
нужен ручной импорт на вкладке «Данные».

## Расчёты (`pkg/calc`, чистые функции)

### FIFO-разнесение выплат — `calc.Allocate(obligations, payments, asOf)`

1. Начисления сортируются по `(due_date, id)`.
2. Сумма всех выплат поставщика («пул») последовательно гасит начисления от самого раннего срока.
   Дата выплаты очередность **не** меняет: предоплата зачтётся в ближайшее по сроку начисление.
3. Остаток пула после всех начислений — **переплата**. Отрицательные выплаты уменьшают пул
   (пул ниже нуля не гасит ничего).
4. Статусы начисления на дату `asOf`:
   - `paid` — открытый остаток 0;
   - `overdue` — остаток > 0 и `due_date < asOf` (+`days_overdue`); в сам день срока — ещё не просрочено;
   - `partial` — остаток > 0, что-то оплачено, срок не наступил;
   - `pending` — остаток = сумме, срок не наступил;
   - `due_soon` — поверх `partial/pending` ставится `MarkDueSoon`, если `due_date ∈ [asOf, asOf+warn_days]`.

### Производные показатели

- **Задолженность** поставщика = `Σ обязательств − Σ выплат` за всё время (столбец B в Excel).
  Может быть отрицательной (переплата).
- **Просрочено** на дату = Σ открытых остатков FIFO со статусом `overdue`.
- **Сводка** (`BuildDashboard`): сумма положительных балансов = «Всего задолженность»;
  «срок сегодня» — открытые с `due_date = asOf`; «7 дней» — `(asOf, asOf+7]`;
  обороты месяца считаются по месяцу `asOf` (начисления по `due_date`, выплаты по `date`);
  списки просроченных (по убыванию дней просрочки) и ближайших сроков (14 дней).
- **Матрица** (`BuildMatrixRange(from, to, asOf)`; `BuildMatrix(year, month, asOf)` —
  совместимая обёртка): суммы по (поставщик, дата) за диапазон; каждый день несёт
  ручной рабочий календарь (`weekday` 1=пн…7=вс; `is_day_off` учитывает сб/вс,
  `settings.holidays` и приоритетные `settings.working_days`; `holiday_name` — из
  `pkg/calc/holidays.go`).
  `cells[].debt_cents` и `day_totals[].debt_cents` — открытые FIFO-остатки начислений,
  срок которых именно этот день, без входящего баланса. `range_balance_cents` —
  сумма таких ежедневных «Долгов» внутри диапазона; `balance_cents` — задолженность
  за всё время (подсказка в GUI); `opening_balance_cents` — баланс до `from`
  (совместимость API, в ежедневный «Долг» не входит);
  `rows[].overdue_cents`/`grand_overdue_cents` — FIFO-просрочка на `asOf`. GUI «Таблицы»
  запрашивает ровно одну неделю с понедельника по воскресенье, передаёт `date=<сегодня>`,
  показывает слева направо поставщика, «Просрочено», «за неделю», а на каждый день —
  «Приход», «Долг», «Оплата»; `is_day_off` используется только для шапки дат,
  поля с суммами не закрашиваются.
- **Прямое редактирование полей «Поставщиков»** реализовано во фронтенде поверх
  существующих CRUD-эндпоинтов и дополняет всплывающую «Поставку»: суммы постоянно
  показаны input-полями, Enter/Tab/потеря фокуса сохраняет, Esc отменяет, пустое
  поле удаляет все операции выбранного вида за день. Одна операция обновляется
  с сохранением документа/комментария/даты поставки (при смене суммы разбивка НДС
  сбрасывается). Для нового прихода и записи без `delivery_date` фронтенд передаёт
  `infer_delivery_date=true`: дата ячейки остаётся сроком оплаты, а сервер
  восстанавливает дату поставки по эффективной отсрочке и ручному рабочему календарю, поэтому
  «Поставщики», карточка поставщика, журнал и экспорт синхронизированы по одной записи.
  Если ячейка является суммой нескольких операций, увеличение создаёт операцию на
  разницу, а уменьшение сокращает/удаляет меньшие записи (сначала без разбивки НДС),
  приводя итог дня к введённой сумме.
- **Карточка** (`BuildSupplierCard`): FIFO-состояния, выплаты по дате, нарастающий баланс
  по хронологии событий (начисление датой `due_date`, выплата датой `date`).

## HTTP API (`pkg/server`)

База: `http://127.0.0.1:<порт>`. Ответы — JSON
(`{"error": "…"}` при ошибке, тексты на русском — они показываются пользователю).
Суммы — `*_cents`, даты — `гггг-мм-дд`.

**Защита локального API:** проверяются `Host` (localhost/127.0.0.1/[::1]/wails.localhost, если не
LAN-режим), `Origin == Host` и — для всех не-GET `/api/*` — заголовок **`X-Oplata-Token`**.
Токен случайный на каждый запуск; фронтенд получает его из `GET /api/bootstrap`
(чужие сайты прочитать не могут из-за Same-Origin). Авторизации пользователей нет и не планируется для локального режима.

| Метод и путь | Описание |
|---|---|
| `GET /api/health` | `{status, version}` |
| `GET /api/bootstrap` | `{version, today, token, settings, warnings, data_file, counts}` — старт GUI |
| `PUT /api/settings` | Частично: `{company_name?, currency_label?, warn_days?, holidays?, working_days?, clear_warnings?}` → bootstrap. `holidays` и `working_days` полностью заменяют соответствующие списки календаря (`[{date,name}]` и `[date]`; даты проверяются/не дублируются/сортируются и не могут пересекаться) |
| `GET /api/suppliers?date=&include_archived=1` | Поставщики со сводками (`calc.SupplierSummary[]`) на дату (по умолчанию сегодня) |
| `POST /api/suppliers` · `PUT/DELETE /api/suppliers/{id}` | CRUD (`name`, `deferral_days`, взаимоисключающие `prepayment`/`on_realization`, `note`, `archived`). Удаление при наличии операций → 400 (предлагается архив) |
| `GET /api/suppliers/{id}/card?date=` | Карточка: FIFO-обязательства, оплаты, график баланса |
| `GET /api/buyers?q=` · `POST /api/buyers` · `PUT/DELETE /api/buyers/{id}` | Справочник покупателей (`name`, `note`; УНП нет). Поиск по наименованию и примечанию. Удаление без ограничений (операций нет) |
| `GET /api/operations?supplier_id=&kind=all\|obligation\|payment&from=&to=&q=&limit=500` | Единый журнал, новые сверху, `{total, operations[]}` |
| `POST /api/obligations` · `PUT/DELETE /api/obligations/{id}` | Приход (начисление). Если `due_date` пуст, но есть `delivery_date` — срок = поставка + эффективная отсрочка (`deferral_days` запроса или поставщика; при предоплате/реализации всегда 0), затем ближайший рабочий день ручного календаря. Если задан `due_date`, `delivery_date` пуст и `infer_delivery_date=true` (ручной ввод из «Поставщиков») — сервер восстанавливает дату поставки от срока по той же эффективной отсрочке. Необязательные `amount_excl_vat_cents`+`vat_cents` должны в сумме давать `amount_cents` (или `amount_cents=0` — сервер посчитает сумму с НДС) |
| `POST /api/payments` · `PUT/DELETE /api/payments/{id}` | Оплата |
| `GET /api/dashboard?date=` | Сводка (`calc.Dashboard`) |
| `GET /api/matrix?from=&to=&date=` | «Поставщики» за диапазон дат (`calc.Matrix`): дни с ручным календарём (`is_day_off`, `holiday_name`…), ежедневный `debt_cents`, просрочка на `date` (по умолчанию сегодня), максимум 371 день. GUI запрашивает одну неделю пн–вс; старый режим `?year=&month=` тоже работает (диапазон = месяц) |
| `POST /api/import?mode=replace\|merge&year=` (multipart `file`) | Импорт XLSX → `excelio.Report`. `replace` сохраняет текущие настройки; `merge` сопоставляет поставщиков по нормализованному имени |
| `GET /api/export.xlsx?year=` | Скачать книгу формата оригинала (+ лист «Операции») |
| `GET /api/export.csv` | Операции CSV (`;`, BOM, суммы с запятой) для Excel RU; последние колонки — сумма без НДС и НДС, если разбивка есть |
| `GET /api/backup.json` | Скачать текущую базу JSON |
| `POST /api/restore` (multipart `file`) | Восстановить базу из JSON (полная замена) |
| `POST /api/reset` `{confirm:"RESET"}` | Пустая база (настройки сохраняются) |
| `POST /api/clear-amounts` `{confirm:"CLEAR_AMOUNTS"}` | Удалить все приходы и оплаты за все даты, сохранив поставщиков, покупателей и настройки; возвращает `removed_obligations`/`removed_payments`, перед записью создаётся автоматический бэкап |
| `GET /` и статика | Встроенный GUI (`pkg/webui/assets`); неизвестный путь → `index.html` |

Фронтенд (`app.js`) — единственная страница, hash-роутинг:
`#/dashboard`, `#/suppliers`, `#/supplier/<id>`, `#/buyers`, `#/operations`, `#/data`;
`#/matrix` оставлен только как совместимый alias экрана «Поставщики».
В синей шапке — кнопки «Карточка поставщика» и «Карточка покупателя» (модальные карточки
справочников: у поставщика выбор из списка, редактируемое наименование и условия оплаты
без поля примечания, у покупателя наименование и примечание; добавить/удалить/сохранить).
Экран `#/buyers` очищен от справочной таблицы и использует ту же недельную сетку, что
«Поставщики»; для покупателей сейчас хранятся только `name`/`note`, операций и сумм нет.
На `#/data` находится годовой календарь-редактор `settings.holidays` и
`settings.working_days`: галочки режима, щелчок по дате, повторный щелчок для отмены,
кнопка сохранения под календарём.
Никаких внешних запросов (полностью офлайн): шрифты системные, библиотек нет.
